# Defragmenter 1.8.0-262

This release closes the post-1.8.0-261 forensic cleanup with the source, tests, release governance and maintained documentation audited together against the canonical Infiltrator Engineering Philosophy.

## Significant changes

- Removed the retired parallel Python application/control/presentation graph instead of retaining a second source of truth beside the native C/C++ product.
- Removed obsolete Python GUI/type-check qualification machinery and source-shape tests whose former subjects no longer exist; retained tests now protect the native public contracts and architectural boundaries.
- Kept filesystem engines and cohesive format-specific code intact where decomposition would only move complexity rather than reduce it.
- Changed the local `.run` builder to materialise its source payload from exact committed Git objects plus the pinned Common gitlink, so untracked runner output and ambient workspace debris cannot enter a release artefact.
- Expanded the qualified release-input boundary so tests, packaging, installation inputs and release-governance scripts are all protected by exact forensic baselines.
- Kept release publication single-build: the quality gate builds and verifies final artefacts once, and the publication workflow can only hand off those exact SHA-bound artefacts.
- Clarified documentation authority so consolidated change history, optional detailed release notes, exact Git tags/releases and the current safety audit no longer compete as alternate release truths.
- Re-audited the resulting repository and advanced both exact source and release-governance baselines to `3f2afe2ab58d5b8276bcfd787a8cc2d77f5ca63f` before making this release decision.

## Deliberately unchanged

- No filesystem parser, placement algorithm, mutation transaction or recovery semantics were changed in this release pass.
- The exact Libraries 1.19.38 pin at `7070c5812b50821fd7580101cb2289a3184f6b2c` remains appropriate; product-specific filesystem semantics stay locally owned.
- The native filesystem engines remain format-local even when large. Their complexity is driven by on-disk formats, transaction safety and verification rather than by an arbitrary file-size target.
- ZFS/OpenZFS and Linux swap remain analysis-only by design.
