## Remove duplicate Amiga disk-signature detection in Test Media — reviewed 2026-11-12

**Exact reviewed source candidate:** `f6477ff808e02610fa7fab259df8ec2868d147a9`, one linear, zero-behind commit after `808b87e1051300070e3a5e092b5a7395f55842c8`. The Common V2 module discovery, trusted path/target policy, journal, filesystem SO engines, release governance and packages are unchanged.

**Ownership defect and correction:** The application previously opened Amiga Test Media volumes and read four bytes at hard-coded offsets to recognise SFS and PFS3 magic. This duplicated filesystem-specific on-disk interpretation and could misroute an unavailable/corrupted provider to an OFS/FFS fallback. Those raw reads, offsets and signature strings are removed from the dispatcher. The caller already owns the exact, immutable fixture catalogue entry (`ofs`, `ffs`, `sfs`, `pfs3`); it now passes that explicit format ID through the populator and both normal and post-defrag verifier calls. The dispatcher accepts only these four identities, rejects unknown/missing identifiers before dispatch, and invokes the matching independent SO's existing fixture/validation API. Filesystem-specific signatures, metadata and payload interpretation remain with their respective provider. The explicit formatter selection and the independent modules' own on-disk identity checks remain unchanged.

**Regression review:** The pre-existing native C Test Media regression was updated in all 20 OFS, FFS, SFS and PFS3 populate/verify call sites to supply its known format identity explicitly. The normal disposable volume format, corruption rejection, byte-integrity and post-defrag tests therefore exercise the same source-owned SOs with no in-application disk signature parser. The worker likewise passes `spec->key` rather than guessing by reading the volume. No physical device or media is automatically opened by this audit.

**Qualification:** This source candidate has **not** been declared fully green by merely updating the audited baseline. A fresh v1.8.0-299 exact-head quality gate, sanitizer suite, independent integration suite and release/publication checks are required. The Common V2 V1 producer migration and physical Latitude 5550 installation verification remain separate, unverified requirements. Governance baseline `6450d98bb2a6e987478417b4636bd8a590c56a89` remains unchanged because no governance path was modified in this source delta.

## EXFAT/EXT missing-provider pre-write refusal — reviewed 2026-11-11

**Reviewed exact source candidate:** `2c5635579b9cd43a99819f0451279863da2f12bd`, a two-commit, zero-behind, linear descendant of the preceding source baseline `92f890fff58eb005fcd4ee0c121c7cf35d82d80a`. No on-disk filesystem algorithm, shared-object library, privilege helper, journal, installer, generic operation engine, or release workflow was changed.

**Precise safety issue and fix:** The Test Media raw host was clearing the first and final MiB of a disposable target before calling some external filesystem modules. It already checked availability for FAT12/16/32, SWAP, XFS, NTFS, ZFS, HFS, HFS+, Btrfs and MINIX, but did not first require a trusted compatible `exFAT.so` or `EXT2.so`/`EXT3.so`/`EXT4.so`. As a result, a missing/incorrect provider could refuse format **after** the generic host had erased target bytes. The updated preflight invokes the existing independent EXFAT and EXT provider-ABI availability checks before the first writable target open. Any absence or ABI mismatch fails closed without altering the input. The module continues to own all filesystem-specific format and layout logic.

**Regression:** New native C Test Media test creates only an 8-MiB temporary file containing sentinels, forces the test module parent to an empty directory, requests each of EXFAT/EXT2/EXT3/EXT4 to create a fixture, and requires a non-successful return with an identical full-file SHA-256 before and after. No real device, elevated privilege or Python test is involved. This ensures the availability guard cannot regress without the build's safety suite detecting it.

**Release and ownership boundary:** The existing generic Test Media signature-clear operation is still present for independently qualified provider creation, and is a separate generic disposable-target preparation policy, not claimed to be filesystem semantics. The previously reviewed Common V2 SWAP and embedded-engine guards remain unchanged. Many other filesystem producers still require their legacy V1 defrag adapters; this specific fix does not claim universal V2 compliance. The `1.8.0-298` full quality, sanitizer and publication checks are **required after this audit update**, and are not presumed to have passed. No on-machine testing on Shannon's Latitude 5550 has been performed.

## Reviewed MMC identity-refresh performance and safety delta — 2026-11-02

Reviewed source candidate: `ea41a641f7d015b8ea9e38fc2351983529e2ef1c`, a direct descendant of the fully released Defragmenter 1.8.0-283 source `4f584cb8b1e8a1c9c8a6e5bc2cae3b3b9eb1242d`.

**Exact reviewed tracked source/test diff:** `defragger/src/core/ld_device.c`, `defragger/tests/test_mounted_image_identity.c`, `defragger/tests/test_architecture.py`. No modifications to `native/filesystem_module_host.c`, target selection, destructive confirmation, external module boundaries, staging, source dependencies, package/install scripts, governance workflow or filesystem engines. The previously audited release-governance baseline `3934c470b7ff3c8411515b37651dc9346c4d99ca` is unchanged.

**Problem:** For an MMC/SD target with no separate serial or WWN in sysfs/udev, the previous stable identity implementation enumerated `/dev/disk/by-partuuid`, `/dev/disk/by-uuid`, `/dev/disk/by-id` and `/dev/mapper` to choose an alias. Every mandatory pre-flush identity refresh repeated this expensive discovery, and OFS issues multiple durable flushes for every metadata mutation.

**Change:** Resolve the kernel-authoritative parent `mmcblkN` sysfs node for a partition `mmcblkNpN` and use its 128-bit physical card CID only when sysfs/udev do not already provide a serial/WWN. Initial open captures `block-hw:mmc-cid:<CID>||<partition-start-sectors>|<partition-bytes>`. Subsequent mandatory pre-`fsync` checks query the card's CID, partition geometry, current open block descriptor's `fstat` rdev, and current `BLKGETSIZE64` ioctl capacity directly. Missing, changed or malformed CID/geometry fails closed without falling back to an alias. Other block devices retain the full prior hardware/alias discovery. Existing `TARGET_IDENTITY_REFRESH_WRITES = 128` unchanged; every sync still calls `ld_device_matches_identity` and `ld_sync_fd`.

**Safety and compatibility:** The original writable `O_EXCL|O_NOFOLLOW` mounted-overlap preflight, exclusive flock, bound descriptor checks, write bounds and existing filesystem-level validation are unchanged. CID binds the physical MMC card, and partition start/size bind the precise partition even after changes in filesystem UUIDs or GPT aliases. Older recorded `block-id` identities may fail closed when a stronger CID is available; do not silently rewrite a journal binding. This does not promise hot-swap protection within the existing bounded 128-write interval, and it does not remove or batch any filesystem durability barrier.

**Regression and evidence boundary:** The native `test_mounted_image_identity.c` fixture now synthesises a partition whose CID exists only on its parent card, verifies full identity formatting, and rejects changed CID, partition start, partition size, malformed and missing CID. `test_architecture.py` preserves the mandatory full sync check and new bounded direct-CID path. These fixtures are nondestructive; CI compilation, native and sanitizer qualification and any speed improvement on the user's actual MMC/SD card must be established separately. The source audit establishes the code-review boundary, not a claim that the physical-medium issue is solved.

## Reviewed incremental performance correction — 2026-11-02

Reviewed source candidate: `3447d1cdd9ccef283b880ff5d55b4d20d41230d2`, directly after approved Defragmenter 1.8.0-282 commit `e7d11e15efc983a08d2b0baf0f726555975eb76d`.

**Review scope:** GitHub's exact source diff changes only `defragger/native/filesystem_module_host.c` and `defragger/tests/test_architecture.py`. No release workflow, package format, filesystem driver source, test-media layout, device opener or module-loading policy changed. No governance-code delta exists beyond the preceding audited governance commit `3934c470b7ff3c8411515b37651dc9346c4d99ca`, which remains the recorded governance baseline.

**Performance bottleneck:** The previous module-host `target_write` called `ld_device_matches_identity` before *every* raw block write. For removable block devices the function can traverse sysfs/udev and `/dev/disk` links to rediscover hardware identity. On Amiga OFS 512-byte writer callbacks, this can dominate all data-transfer time. The new module host binds `bound_identity` and the descriptor's dev/inode/major:minor to the original, mounted-overlap-checked, O_EXCL-opened target. Each write checks the descriptor's current `fstat` identity, original capacity and original immutable identity string. Full hardware identity discovery occurs no less often than every 128 successful writes and before every durability `sync_target` barrier, failing closed on a mismatch. This is a deliberate bounded safety/performance tradeoff: it preserves continuous *open object* checks and periodic *external hardware identity* checks, but is **not identical** to the former full external-discovery-before-every-block policy.

**Safety checks preserved:** `ld_device_try_open` still rejects mounted or conflicting devices and opens writable block devices O_EXCL with O_NOFOLLOW; `target_open` still verifies expected binding/size and obtains the mandatory non-blocking advisory lock. The write host checks `writable`, exact target capacity, kernel opened-object type, st_dev, inode and rdev, and byte bounds before `pwrite`. Sync revalidates full hardware identity before `fsync`. Filesystem-specific format signatures and exact geometry validation are unchanged, and a stale/invalid binding refuses further writes. A true hot-swap within a 128-write window is a residual risk that was previously checked more frequently; hardware qualification remains necessary.

**Regression:** `tests/test_architecture.py` now specifically enforces the bounded refresh threshold, fstat/inode/device checks, immutable identity equality, successful-write accounting, full identity check before sync, and retention of the exclusive-open lock. The pre-existing mounted-image, hard-link, locked 2 GiB OFS fixture, complete filesystem, native-media and ASan/UBSan tests remain intact. Candidate [source quality run 41400237099](https://github.com/Infiltrator-Projects/Defragmenter/actions/runs/41400237099) qualifies this exact source; publication of the subsequent VERSION-only release requires its own successfully completed full gate, without exception.

**Assurance limits:** No real SD-card latency benchmark or physical media write/erase test has been performed by this source review. The original physical OFS formatter failure and observed slowness must be checked on the user-confirmed sacrificial media after the qualified release is installed. A source change and a green synthetic test are not proof of that physical outcome.

## Safety invariants

- Every new write requires qualified native filesystem analysis, exact format/geometry, stable device identity and capacity, mounted-overlap refusal and a supported plan.
- Unsupported features, inconsistent metadata, unknown target identity or a required missing/untrusted/ABI-incompatible `.so` cause **pre-write refusal**. No private-engine fallback.
- Recovery material and verified staging are persisted before authoritative source mutation can require rollback; transaction phases are checked and Stop is honoured at safe/recoverable boundaries.
- Recover can be admitted from a valid pre-existing user-bound journal even when fresh source analysis is impossible. The journal, target identity, staged bytes and phase are validated by the actual native worker.
- Final success requires reopening the result and checking canonical placement, exact Growth reserve where available, structural integrity and complete logical payload identity.
- Filesystem-neutral Linux topology checks distinguish partition parents, holders and whole/stacked-device slaves; hard-link aliases cannot bypass image mount checks.

These invariants apply across the bounded FAT12/16/32, exFAT, NTFS, EXT2/3/4, XFS v5, Amiga OFS/FFS/SFS/PFS3, HFS/HFS+, Btrfs, APFS, Minix and UFS variants wherever write operations are admitted. Special format states not explicitly qualified fail closed. **ZFS/OpenZFS and swap remain analysis-only.**

## Filesystem module and Test Media boundaries

The intended single-owner design is documented in [Filesystem Engine Ownership](FILESYSTEM_ENGINE_OWNERSHIP.md). Migrated SO-backed production workers must execute the actual external module with trusted path/version/ABI checks; test environments use isolated SO roots. FAT and OFS Test Media formatting/population are module-owned. Migration may not quietly retain a second production formatter, writer or journal engine.

The 21 Test Media slots must keep their independent first-party C creator/raw verifier, deterministic 200 MiB plus boundary-file corpus, schema 3 disk-identity binding, full-byte verification and corruption refusal. A successfully formatted image or a saved results file alone is not evidence of correctness.

## Release and physical assurance

Development uses direct-to-protected `main`. A `defragger/VERSION` change requests a release; ordinary documentation updates do not. Both permanent self-hosted quality/sanitizer lanes, exact source/governance baseline comparisons and protected linear history must qualify the same intended commit. Publication uses only its once-built SHA-bound `.deb`, `.run` and manifest; version identity and digests are write-once. Public APT propagation is observed separately.

Synthetic, sanitizer and dm-log-writes tests are important evidence but are **not** physical-media power-loss proof. No completed source audit, published release or passing test alone claims universal on-disk write safety.
